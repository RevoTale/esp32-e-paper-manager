## Що перевірено

- [Фінальне пакування](../build/native-release-candidate.log): exit 0;
  повний quality gate — PASS за 74 с; changed coverage 91,9%, загальне 92,1%.
  Строгий lint, unit/integration/race, перевірка модулів і TinyGo build пройшли.
- Обидва [Linux](../build/native-candidate.gEnGoa/vulnerabilities-linux.txt) /
  [macOS](../build/native-candidate.gEnGoa/vulnerabilities-darwin.txt) аудити:
  `No vulnerabilities found`. Це перевірка відомих вразливостей, не гарантія
  від усіх можливих атак. Go 1.26.8, TinyGo 0.41.1; host runtime — CGO=0.
- Усі 130 записів SHA256SUMS — OK. Знімок Go-коду повторно звірений після
  збірки; перевірки небезпечних назв, symlink, прав доступу, повторного
  використання каталогу й посилань пакета пройшли без вимкнення тестів.
- `picotool info -a` читав **файл**, не пристрій: family `rp2350-arm-s`,
  target RP2350. Хеш UF2 збігається з уже перевіреною resource-збіркою.
- Обидва PNG відкриті й перевірені: український текст, блоки та кутова дата
  читаються. Дата в preview синтетична; сірий `#111` і фон `#ddd` навмисно
  стають dithering-патернами. Для суцільно чорних літер використовуй `black`.
- Реальні секції ELF відповідають [resource-звіту](native-firmware-resources.md).
  8 512 байтів з короткого виводу TinyGo **не є** повним або піковим RAM.

Перший запуск пакування впіймав залежний від umask тест: `WriteFile(0644)` під
`umask 077` створював 0600, тобто негативна перевірка не мала публічного файлу.
Додано явний `Chmod(0644)` лише до fixture в `t.TempDir()`. Відтворення,
manager race/lint та незалежний перегляд пройшли; production-захист не змінено.
[Початковий звіт](../build/native-release-final.log) збережено.

## Ручне приймання

1. Виконано: встановлено native UF2 вище; прийняті піни/HAT/FPC не змінено.
2. Виконано: виправлений native USB sender показав HTML, підтверджений кадр.
3. Після готовності повторити зміну, перевірити час повного циклу й reconnect.
4. Окремо прийняти WPA3/provisioning, USB-пріоритет і відновлення після обриву.

Прошивка чекає sender: автоматичної картинки після boot немає. Часткове
оновлення й IPv6 на Pico поки вимкнені. Фізичний запас RAM/stack, радіовідновлення
та енергоспоживання ще не виміряні. Інші межі — в інструкції запуску.
Контрольний коміт попереднього стану — `37a1471`. Міграцію та перший прийнятий
USB-показ закомічено й відправлено в `origin/main` як `66dc9a1` після явного
дозволу користувача. Це не закриває решту апаратного приймання E5.

## Перша спроба фізичного приймання, 2026-09-07

- Користувач перебудував Dev Container і дозволив прямий macOS USB, прошивання
  та одну HTML-передачу. Новий контейнер `2b739d1fc4c5` відновив Go 1.26.8 /
  TinyGo 0.41.1; `go test ./screenwire` — PASS. Хеш UF2 не змінився.
- macOS бачив `/dev/cu.usbmodem101`, VID/PID `2e8a:000a`, Generic CDC.
  `stty -f /dev/cu.usbmodem101 1200 hupcl` повернув exit 0. З'явився
  `/Volumes/RP2350/INFO_UF2.TXT`: Model Raspberry Pi RP2350, Board-ID RP2350.
- Виконано одне `cp` готового UF2 на цей диск. Воно повернуло exit 1:
  `Device not configured`. Диск зник; CDC не повернувся в обмеженому очікуванні.
  Наступна перевірка не знайшла Pico на macOS USB bus або в контейнері.
- Запис flash міг відбутися частково або повністю; виконання нової прошивки
  не підтверджене. Причину ще не встановлено. **HTML не передавали.**
- Не було повторного запису, зміни GPIO/HAT/FPC, стирання flash чи Attach/Detach.
  Наступна дія — фізично повернути Pico в BOOTSEL та повторно визначити стан.
  Прийнятий EPS1 UF2 з хешем `a17ae2a2…a92185f` збережений для відновлення.

Цей запис доповнює попереднє програмне приймання, не підміняє його фізичним.
Готовий пакет та SHA256SUMS залишені незмінними.

## Повтор після ручного BOOTSEL, 2026-09-07

- Користувач повторно підключив Pico з BOOTSEL. INFO_UF2 знову підтвердив
  Raspberry Pi RP2350 / Board-ID RP2350. Виконано один контрольований запис
  **того самого UF2**, цього разу `cp` завершився з exit 0.
- Диск зник, але жоден `/dev/cu.usbmodem*` не з'явився за 10 секунд пошуку.
  Наступні перевірки macOS USB bus і USB/serial у контейнері теж не знайшли Pico.
  **Копіювання без помилки не підтверджує роботу прошивки.**
- EPS2 Hello/Health і HTML не передавали: доступного USB-порту немає.
  Причина невідома; це ще не доказ проблеми екрана, пайки чи рендерингу.
- Наступна перевірка — звичайне від'єднання/під'єднання USB **без BOOTSEL**,
  без акумуляторів і без зміни проводів. Перевіряємо холодний запуск перед
  новими змінами чи повторним прошиванням. E5 залишається відкритим.
- Не змінювали код, піни, HAT/FPC, готовий пакет або recovery UF2; flash
  не стирали, Attach/Detach не використовували.

Подальше спостереження користувача: з BOOTSEL пристрій з'являється, без нього
не визначається. Це відокремлює ROM-завантажувач від звичайного запуску, але
ще не встановлює причину. Read-only перевірка підтвердила `-target=pico2-w`
та успадковане `serial: usb` у TinyGo 0.41.1. Код і прошивку не змінювали;
наступне контрольне порівняння — зі збереженою відомою робочою прошивкою,
а не ще один сліпий запис кандидата. Деталі й офіційне джерело — у
[журналі](../../../docs/epaper-debugging-history.md).

## Локалізація раннього запуску, 2026-09-07

Окремий [startup-probe](startup-probe.md) завантажено одним прямим macOS `cp`
з exit 0; USB повернувся. Після поетапних підтверджень отримано `DONE panel_io`,
але після `BEGIN flash_uid` та дозволу виконати цей крок відповіді вже немає.
Це межа `pico2w.UID()` / `machine.DeviceID()`, а не передача картинки чи Wi-Fi.
Точна внутрішня причина ще не встановлена. Журнал сесій, радіо та оновлення
екрана не запускалися; ID і секрети не виводилися. Кандидат та recovery UF2
незмінні, його фізичне приймання не зараховано. Тести діагностики й повний
quality gate пройшли; обхід перевірок безпеки або вимкнення тестів не робили.

Знайдено відповідний upstream [баг #5408](https://github.com/tinygo-org/tinygo/issues/5408)
і [виправлення #5413](https://github.com/tinygo-org/tinygo/pull/5413), включене
в стабільний TinyGo 0.42.0. Наш 0.41.1 ще має старий код. Це сильна підозра,
але нову версію на цьому Pico не перевіряли. Деталі та план порівняння —
в [діагностиці](startup-probe.md). Єдина спроба програмного USB-reset зависла
та була перервана (exit 130), BOOTSEL-диск не з'явився. Для відновлення потрібне
ручне перепідключення з BOOTSEL; фонових команд запису або reset не залишено.

### Відновлення після діагностики

Після підтвердженого користувачем BOOTSEL один `cp` збереженого EPS1 UF2
повідомив про помилку копіювання додаткових атрибутів macOS (exit 1), але USB
повернувся. Замість повторного прошивання виконано один Hello: `EPS1`, `idle`,
800×480, 100 байтів на chunk, два проходи, інтервал 180 с, CRC правильний;
клієнт завершився з exit 0. Нову картинку не передавали. Це підтверджене
відновлення протоколу, не приймання EPS2 або нових пікселів.

Dockerfile тепер використовує офіційний образ TinyGo 0.42.0. Поточний контейнер
ще має 0.41.1: перебудова, тести з новою версією та повтор UID-проби попереду.
Готовий пакет кандидата та його контрольні суми не змінені.
